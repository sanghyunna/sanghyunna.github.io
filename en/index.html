SK enmove · AX Team · 2026

Status: Deployed · In use

2 hrs → 3 minTime per update

Weekly production plan automation

Automated the data preparation that production planners did by hand in Excel every week.

  1. Problem

    Each time planners updated the plan, they downloaded the columns they needed from the ERP one by one and combined them in Excel. Each round took about 2 hours.

  2. Analysis

    The ERP screens were slow, and the data could not be downloaded in the table format the planners used. Some figures were not available in the ERP, so the planners requested them by email.

  3. What I did

    I built a Databricks pipeline that pulls the ERP data and moved the Excel processing steps into pandas code. For the figures that arrive by email, I wrote a parser that extracts values with fixed rules. These figures set production volume, so the same email must always give the same values. For that reason I did not use an LLM, whose output can change between runs.

  4. Result

    After deployment, all 3 people on the planning team use this tool for the weekly plan. Each update now takes about 3 minutes instead of about 2 hours.

Status: Deployed · In use

Weekly → Real timeStock data updates

Raw material purchasing support tool

A tool that calculates the stock status and recommended order dates a buyer needs when deciding when to order raw materials.

  1. Problem

    The buyer decides when to order by looking at the production plan and raw material stock together. The data had to be downloaded from several systems and combined in Excel pivot tables, so a check that should happen daily was done once a week.

  2. Analysis

    The buyer looked at the same values each time: recent production, production in the same month last year, current stock, and the delivery lead time for each material. All of these could be calculated from data already in the systems.

  3. What I did

    The tool shows live stock charts for each material, with a dotted line for projected stock at the current usage rate. It calculates the average lead time from past order and receipt records. It then works out the latest date to order so that stock stays above a set minimum, and shows that date as the recommended order date.

  4. Result

    The tool also drafts the purchase request email, and the buyer checks it and sends it. The tool is deployed and used for actual purchasing decisions.

SK enmove · AX Team · 2026

Status: In operation · Used in inventory planning

4 months aheadSales forecast per product

Product-level sales demand forecasting

Forecast product-level sales four months ahead so that production can be prepared early.

  1. Problem

    Preparing production early required product-level sales several months ahead, but the company had no official forecast. There was also no baseline to compare a model against.

  2. Analysis

    I first computed the method staff used to estimate sales (a 3-month average around the same month last year) and used it as the baseline. Data errors, such as one product listed under two codes, were checked with the staff and fixed one by one.

  3. What I did

    I compared a LightGBM model I built with Chronos-2, a pretrained time-series model. LightGBM had lower error in one evaluation period but much higher error in the other. Chronos-2 had similar error in both periods, so I chose Chronos-2 as the production model.

  4. Result

    The models were backtested on about 90 months of data split into periods. The forecasts are now used in inventory planning.

DetailsHide
  • LightGBM feature importance was concentrated on past sales, so using an interpretable model gave little extra benefit.
  • Many products sell close to zero, so I used WAPE on total volume instead of MAPE.
  • While improving LightGBM, I tested Tweedie loss, RevIN, multiple seeds, and ensembles. The final production model is Chronos-2.
  • Time series
  • Chronos-2
  • LightGBM
  • Backtesting

Personal open source · 2026.06 —

Status: Released · Under review for internal use

Readable Studio

A document editor that lets you change AI-generated HTML documents directly on screen, as in PowerPoint.

  1. Problem

    At work, documents are increasingly given to AI to summarize or extend. Word documents are easy for AI to process but hard to emphasize visually. PowerPoint documents are easy to emphasize but hard for AI to process.

  2. Analysis

    I used the post “The unreasonable effectiveness of HTML” by Thariq of the Claude Code team as a reference. HTML documents are easy for AI to process and can also carry the visual formatting a report needs.

  3. What I did

    Generating an HTML report draft with AI was easy, but even small fixes, such as a typo or a card position, had to be requested from the AI again. I forked the open-source open-design (Apache-2.0) and added editing features that save on-screen changes to the HTML source file.

  4. Result

    A Windows build (v1.2.1) is published on GitHub. I use it myself and fix problems as I find them, and the company is reviewing whether to adopt it.

DetailsHide
  • On screen you can edit text, formatting, color, spacing, borders, and opacity, move and resize elements, use alignment guides and snapping, duplicate and delete, and undo and redo.
  • Each editable element gets a unique ID, so changes made on screen are written to the matching place in the HTML source. The AI then continues from the source as the person edited it.
  • Each conversation with the AI creates a Git commit, so you can roll back if the AI breaks the output.
  • Manual edits are written to the file only when you press Save or Cancel. The tool keeps a SHA-256 hash of the file from when editing started. If another process changed the file in the meantime, the save stops so neither version is overwritten.
  • I split one large JavaScript bundle into smaller parts that load when needed and removed unused features, so the app runs on slow virtual desktops (VDI).

Chung-Ang University Cognitive Intelligence Lab · Undergraduate Researcher

2025.10 — 2026.03

Improving relation errors in CLIP

CLIP often cannot tell apart two sentences with the same words but opposite relations (for example, “B on A” and “A on B”). Without retraining the model, I improved accuracy by changing how the image-text similarity score is computed.

DetailsHide
  • I applied whitening and SVD to the covariance of calibration image-text pairs and designed a new training-free score, Ω.
  • Using Ω in place of cosine similarity in every case hurt general retrieval. So Ω only re-ranks the top 2 cosine candidates, and only when its evidence is more consistent.
  • Accuracy on the ARO benchmark rose by about 3 points with no extra training, and general retrieval on MSCOCO and Flickr30k dropped by less than 0.3 points. I wrote a paper draft that covers where the method works and where it does not.
  • CLIP
  • VLM
  • Compositionality

Chung-Ang University Multimodal AI Lab · Undergraduate Researcher

2025.02 — 2025.10

Diagnosing a failed LLaVA training run

While fine-tuning LLaVA-1.5 7B with LoRA, the loss suddenly rose and training failed. Before changing settings, I checked the W&B training logs to narrow down the cause.

DetailsHide
  • The loss rose during the period when the learning rate stayed at its peak, not right after warmup, and it never returned to its earlier level. I listed possible causes such as data issues, numerical instability, and checkpoint resume state, and checked the most likely one first: a learning rate that was too high.
  • I kept the learning-rate schedule and lowered only the peak LoRA learning rate from 2e-4 to 2e-5. Training became stable and reached the performance reported in the paper.
  • I adapted the public multi-GPU setup to a single personal GPU (RTX 5090) with DeepSpeed ZeRO-2 and gradient checkpointing. I also added vLLM serving, which the official repository lacks, to run the benchmarks.
  • LLaVA
  • LoRA
  • Training stability

Chung-Ang University Super-Intelligence Computing Lab · Researcher

2024.09 — 2025.02

Public facility siting module (government project)

A project to recommend locations for public facilities for several local governments. The data had few variables and many missing values, so instead of recommending locations directly, I treated it as a regression problem that predicts expected usage for each candidate site.

DetailsHide
  • Before removing areas with unusually high usage for their population as outliers, I checked them and found they were office districts. I asked the local government for bus boarding data to add floating population, which lowered MAPE by 20 points.
  • Recommendations clustered in one area. I fixed this by assuming a facility was built at the first candidate, recalculating demand, and repeating.
  • I agreed on input and output formats with the backend developer, built an API that shows recommended sites on a map, and delivered it with a report.
