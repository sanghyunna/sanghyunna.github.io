주간 생산계획 조정 자동화

생산계획 담당자가 매주 엑셀로 하던 데이터 정리를 자동화했습니다.

  1. 문제

    생산계획 담당자는 계획을 조정할 때마다 ERP에서 필요한 열을 하나씩 내려받아 엑셀에서 합쳤습니다. 한 번에 약 2시간이 걸렸습니다.

  2. 분석

    ERP 조회 화면이 느리고 담당자가 쓰는 표 형태로는 데이터를 내려받을 수 없었습니다. 일부 수치는 ERP에서 받을 수 없어 담당자가 메일로 요청해 받고 있었습니다.

  3. 한 일

    Databricks에서 ERP 데이터를 받아 오는 파이프라인을 개발하고 담당자가 엑셀에서 하던 가공 과정을 pandas 코드로 옮겼습니다. 메일로 받은 수치는 정해진 규칙으로 값을 뽑는 파서를 작성해 반영했습니다. 이 수치로 생산량을 정하기 때문에 같은 메일에서는 항상 같은 값이 나와야 했습니다. 그래서 결과가 매번 달라질 수 있는 LLM은 쓰지 않았습니다.

  4. 결과

    배포 후 담당 팀 3명이 모두 이 도구로 주간 계획을 조정하고 있습니다. 1회 작업 시간은 약 2시간에서 약 3분으로 줄었습니다.

원재료 구매 판단 지원 도구

구매 담당자가 원재료 주문 시점을 정할 수 있도록 재고 현황과 주문 권장일을 자동으로 계산해 보여 줍니다.

  1. 문제

    구매 담당자는 생산 계획과 원재료 재고를 함께 보고 주문 시점을 정합니다. 필요한 데이터는 여러 시스템에서 하나씩 내려받아 엑셀 피벗으로 합쳐야 해서 작업량이 많았습니다. 그래서 매일 해야 하는 확인을 주 1회로 줄여서 하고 있었습니다.

  2. 분석

    담당자가 매번 확인하는 값은 최근 생산량, 작년 같은 달 생산량, 현재 재고, 원재료별 납품 소요 기간(리드타임)이었습니다. 이 값은 모두 시스템에 있는 데이터로 계산할 수 있었습니다.

  3. 한 일

    원재료별 재고를 실시간 차트로 보여 주고 지금 사용량이 계속될 때의 예상 재고를 점선으로 함께 그렸습니다. 과거 주문·입고 기록으로 평균 리드타임을 구한 뒤 재고가 정해 둔 최저선 아래로 내려가지 않으려면 언제 주문해야 하는지 계산해 주문 권장일로 표시했습니다.

  4. 결과

    구매 요청 메일 초안도 자동으로 만듭니다. 담당자는 내용을 확인한 뒤 직접 보냅니다. 이 도구는 배포되어 실제 구매 판단에 쓰이고 있습니다.

제품별 판매량 수요예측

생산을 미리 준비할 수 있도록 제품별 판매량을 4개월 앞서 예측했습니다.

  1. 문제

    생산을 미리 준비하려면 제품별 판매량을 몇 달 앞서 알아야 했지만 회사에는 공식 예측값이 없었습니다. 모델을 만들어도 성능을 비교할 기준이 없는 상태였습니다.

  2. 분석

    먼저 실무자가 판매량을 짐작할 때 쓰던 방식(전년 같은 달 기준 3개월 평균)을 그대로 계산해 비교 기준으로 정했습니다. 같은 제품에 다른 코드가 붙어 있는 것 같은 데이터 오류는 실무자와 하나씩 확인해 고쳤습니다.

  3. 한 일

    직접 만든 LightGBM 모델과 시계열 사전학습 모델인 Chronos-2를 비교했습니다. LightGBM은 한 평가 기간에서 오차가 더 작았지만 다른 평가 기간에서는 오차가 크게 늘었습니다. Chronos-2는 두 기간의 오차가 비슷했습니다. 그래서 평가 기간이 바뀌어도 성능 차이가 작은 Chronos-2를 운영 모델로 정했습니다.

  4. 결과

    약 90개월 치 데이터를 기간별로 나눠 백테스트했습니다. 예측값은 현재 재고 운영에 반영되고 있습니다.

자세히접기
  • LightGBM의 피처 중요도는 대부분 과거 판매량에 집중되어 있었습니다. 해석 가능한 모델을 쓰는 이점이 크지 않다고 판단했습니다.
  • 판매량이 0에 가까운 제품이 많아 평가 지표로 MAPE 대신 전체 물량 기준의 WAPE를 썼습니다.
  • LightGBM을 개선하는 과정에서 Tweedie 손실, RevIN, 여러 시드와 앙상블을 실험했습니다. 최종 운영 모델은 Chronos-2입니다.

Readable Studio

문서 편집 도구입니다. AI가 만든 HTML 문서를 PowerPoint처럼 화면에서 직접 고칠 수 있습니다.

  1. 문제

    회사에서 문서를 AI에 넣어 요약하거나 이어서 작성하는 일이 늘었습니다. Word 문서는 AI가 처리하기 쉽지만 내용을 시각적으로 강조하기 어렵습니다. PowerPoint 문서는 강조하기 쉽지만 AI가 처리하기 어렵습니다.

  2. 분석

    Claude Code 팀의 Thariq가 쓴 글 “The unreasonable effectiveness of HTML”을 참고했습니다. HTML 문서는 AI가 처리하기 쉬우면서 보고서에 필요한 시각 표현도 할 수 있습니다.

  3. 한 일

    AI로 HTML 보고서 초안을 만드는 것은 쉬웠지만 오탈자나 카드 위치 같은 작은 수정도 매번 AI에 다시 요청해야 했습니다. 오픈소스 open-design(Apache-2.0)을 포크해 화면에서 직접 고친 내용이 HTML 원본 파일에 저장되는 편집 기능을 추가했습니다.

  4. 결과

    Windows용 실행 파일(v1.2.1)을 GitHub에 공개했습니다. 직접 쓰면서 문제를 고치고 있습니다. 회사에서는 도입 여부를 검토하고 있습니다.

자세히접기
  • 텍스트·서식·색상·간격·테두리·투명도 수정, 이동, 크기 조절, 정렬 기준선과 자석 정렬, 복제·삭제, 실행 취소와 다시 실행을 화면에서 할 수 있습니다.
  • 편집할 수 있는 요소마다 고유 ID를 붙여 화면에서 고친 내용을 HTML 원본의 해당 위치에 반영합니다. 그래서 AI도 사람이 고친 원본을 기준으로 이어서 작업합니다.
  • AI와 대화할 때마다 Git 커밋을 만들어 AI가 결과물을 망가뜨려도 이전 상태로 되돌릴 수 있습니다.
  • 직접 편집한 내용은 저장이나 취소를 눌러야 파일에 반영됩니다. 편집을 시작한 시점의 원본 해시(SHA-256)를 보관합니다. 저장할 때 그사이 다른 작업이 파일을 바꿨다면 저장을 멈춰 어느 쪽 내용도 덮어쓰지 않게 했습니다.
  • 하나로 묶여 있던 큰 JavaScript 파일을 나누고 필요할 때 불러오도록 바꿨습니다. 쓰지 않는 기능도 지워서 느린 가상 데스크톱(VDI)에서도 쓸 수 있게 했습니다.

Text-to-SQL 에이전트

SK엔무브 · 팀 과제상태: 보류

실무자의 질문을 SQL로 바꿔 사내 데이터를 조회하는 에이전트입니다. 예시로는 질문과 정답을 짝지은 데이터 대신 쿼리 4~5개를 넣었습니다. 이 쿼리들은 여러 테이블을 어떻게 조인하는지 보여 줍니다. 그 뒤로 에이전트가 예시에 없던 실무자 질문에도 맞는 SQL을 만들기 시작했습니다.

에이전트가 쓰는 서비스 계정에는 조회 권한만 주었습니다. 에이전트용 도구도 조회만 가능하게 직접 작성했습니다. 데이터 레이크에 올라간 테이블이 아직 적어 과제가 보류된 상태입니다.

Multi-Agent Debate와 LLM Council 관련 자료를 참고했습니다. 데이터 출처별로 에이전트를 나누는 방식은 이 과제에 맞게 정했습니다.

CLIP의 관계 판별 오류 개선

CLIP은 단어는 같고 관계만 반대인 두 문장(예: “A 위의 B”와 “B 위의 A”)을 잘 구분하지 못합니다. 모델을 다시 학습하지 않고 이미지와 문장의 유사도 점수를 계산하는 방식을 바꿔 두 문장을 구분하는 정확도를 높였습니다.

자세히접기
  • 보정용 이미지·문장 쌍의 공분산에 화이트닝과 SVD를 적용해 새 점수 Ω를 설계했습니다. Ω는 추가 학습 없이 계산할 수 있습니다.
  • Ω를 모든 경우에 코사인 유사도 대신 쓰면 일반 검색 성능이 크게 떨어졌습니다. 그래서 코사인 유사도 상위 2개 후보를 비교할 때 Ω의 판단 근거가 더 일관된 경우에만 Ω로 순위를 다시 정하게 했습니다.
  • ARO 벤치마크에서 추가 학습 없이 정확도를 약 3%p 높였습니다. 같은 방법을 MSCOCO·Flickr30k 일반 검색에 적용했을 때 성능 하락은 0.3%p 미만이었습니다. 방법이 잘 작동하는 조건과 작동하지 않는 조건을 함께 정리해 논문 초안을 썼습니다.

자세히접기
