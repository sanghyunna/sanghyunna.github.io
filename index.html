Readable Studio

AI가 초안을 쓰고, 사람은 PowerPoint처럼 직접 고치는 HTML 문서 도구.

왜 오탈자 하나, 10픽셀 이동까지 AI와 다시 대화해야 할까?

  1. 발견

    보고서 형식의 딜레마. Word는 AI가 다루기 좋지만 시각적 강조가 약하고, PowerPoint는 그 반대다. AI가 문서를 읽고 이어 쓰는 일이 늘수록 이 간극이 커졌다.

  2. 이해

    HTML이면 둘 다 된다. Claude Code 팀 Thariq의 글 “The unreasonable effectiveness of HTML”에서 실마리를 얻었다. HTML이면 사람과 AI가 같은 파일을 읽고, 표현력도 보고서 수준으로 충분하다.

  3. 구현

    병목은 생성이 아니라 마지막 손질이었다. 오탈자 하나에도 프롬프트를 다시 써야 했다. 오픈소스 open-design(Apache-2.0)을 포크해, 화면에서 고친 내용이 HTML 원본에 바로 기록되는 편집 레이어를 붙였다.

  4. 정착

    공개했고, 직접 쓰며 다듬는 중. Windows용 portable 빌드로 공개했고, 사내 도입을 검토하고 있다.

자세히접기
  • 이동·크기 조절·정렬 가이드와 스냅, 서식·색상·간격·테두리·투명도, 복제·삭제, 실행 취소와 다시 실행을 화면에서 직접 편집한다.
  • 편집 가능한 요소에 안정적인 식별자를 붙여, 화면에서 바꾼 내용을 HTML 원본의 해당 노드에 패치한다. AI는 사람이 고친 원본을 기준으로 이어서 작업한다.
  • LLM 채팅마다 Git 커밋 지점을 남겨, AI가 결과물을 망가뜨려도 이전 상태로 되돌린다.
  • 수동 편집은 명시적으로 저장하거나 취소한다. 편집 시작 시점 원본의 SHA-256을 보관해, 그사이 파일이 바뀌었으면 저장을 멈추고 사용자의 편집은 그대로 둔다.
  • 거대한 단일 JavaScript 번들을 코드 스플리팅과 지연 로딩으로 나누고 쓰지 않는 기능을 걷어내, 느린 가상 데스크톱(VDI)에서도 쓸 수 있게 했다.

2시간 → 3분매번 하던 수작업

주간 생산계획 조정 자동화

느린 ERP 조회와 엑셀 수작업을 데이터 파이프라인으로. 메일로 받은 수치까지 자동 반영한다.

  1. 발견

    매번 약 2시간의 수작업. 담당자는 원하는 형태로 데이터를 주지 않는 느린 ERP에서 열을 하나씩 내려받아, 엑셀에서 손으로 이어 붙였다.

  2. 이해

    데이터는 이미 있었다. 문제는 받아오는 길과 가공 방식이었다. 파이프라인으로 받을 수 없는 값은 담당자 메일에 숫자로 들어오고 있었다.

  3. 구현

    파이프라인, pandas, 규칙 기반 파서. Databricks로 데이터를 받고 엑셀에서 하던 가공을 pandas로 옮겼다. 메일 속 수치는 LLM 대신 규칙 기반 파서로 뽑았다. 결과가 곧 생산량이 되는 업무라 같은 입력에는 같은 답이 나와야 했다.

  4. 정착

    약 2시간 → 약 3분. 배포 후 담당 현업 팀 전원이 이 도구로 계획을 조정한다.

자세히접기
  • 판단 기준은 “AI를 쓸 수 있는가”가 아니라 “여기서 비결정성이 허용되는가”였다.
  • Databricks
  • pandas
  • 데이터 파이프라인

주 1회 → 실시간재고 판단 주기

원재료 구매 의사결정 지원

매일 해야 하지만 주 1회로 미루던 판단을, 실시간 재고 화면과 주문 권장일로.

  1. 발견

    매일 할 판단을 주 1회로 미루고 있었다. 구매 담당자는 생산 계획과 원재료 재고를 함께 보고 구매를 정한다. 느린 시스템에서 하나씩 내려받아 엑셀 피벗으로 합치는 일이라 매일 하기엔 공수가 너무 컸다.

  2. 이해

    사람이 매번 하던 계산을 미리 해 둔다. 판단 재료는 최근 생산량, 작년 같은 달 생산량, 현재 재고, 산지에 따라 달라지는 리드타임이었다.

  3. 구현

    실시간 재고 화면과 주문 권장일. 원재료별 재고를 실시간 차트로 보여 주고, 현재 사용 추세로 앞으로의 재고를 점선으로 그린다. 과거 주문·입고 기록으로 평균 리드타임을 구하고, 위험선에서 거꾸로 계산해 주문해야 할 날을 띄운다.

  4. 정착

    초안을 검토하고 전송만. 구매 요청 메일 초안까지 자동으로 쓰고, 담당자가 확인해 보낸다. 배포되어 실제 구매 판단에 쓰이고 있다.

자세히접기
  • 자동화는 판단 재료와 초안까지. 최종 전송은 담당자가 한다(human-in-the-loop).
  • 생성형 AI가 아니라 데이터 엔지니어링과 규칙 기반 계산으로 푼 문제다.
  • 데이터 파이프라인
  • 대시보드
  • 리드타임 역산
  • Human-in-the-loop

4개월 선행제품별 판매량 예측

판매량 수요예측

비교 기준조차 없던 예측 문제. 직접 만든 모델보다, 기간이 바뀌어도 흔들리지 않는 모델을 골랐다.

  1. 발견

    예측값도, 비교할 기준도 없었다. 생산을 미리 준비하려면 제품별 판매량을 몇 달 앞서 알아야 했다.

  2. 이해

    비교 기준부터 세웠다. 현업이 실제로 참고하던 방식(전년 같은 달 3개월 평균)을 그대로 계산해 기준으로 삼았다. 같은 제품에 다른 코드가 붙는 식의 데이터 오류는 현업과 하나씩 추적해 정정했다.

  3. 구현

    내가 만든 모델 대신, 흔들리지 않는 모델. 직접 만든 LightGBM은 한 평가 기간에서 더 좋았지만, 기간을 바꾸자 오차가 눈에 띄게 흔들렸다. 시계열 파운데이션 모델 Chronos-2는 두 기간 모두 비슷한 수준을 지켰다.

  4. 정착

    재고 운영에 반영. 약 90개월 데이터로 기간을 나눠 백테스트했고, 제공한 예측값은 실제 재고 운영에 쓰이고 있다.

자세히접기
  • LightGBM의 피처 중요도는 대부분 과거 판매량에 쏠려 있었다. “해석할 수 있다”는 장점이 현업에 줄 정보가 크지 않았다.
  • 판매량이 0에 가까운 제품이 많아 MAPE 대신 전체 물량 기준의 WAPE로 평가했다.
  • LightGBM 후보를 다듬으며 Tweedie 손실, RevIN, 여러 시드와 앙상블을 실험했다. 최종 모델의 성과와는 별개다.
  • 시계열
  • Chronos-2
  • LightGBM
  • 백테스트

자세히접기

  • 발산은 warmup 직후가 아니라 최고 학습률에 머무는 구간에서 시작됐고, 손실이 원래 수준으로 돌아오지 않았다. 데이터·수치 불안정·재개 상태 같은 후보를 늘어놓고, 가장 직접적인 가설인 학습률 과다를 골랐다.
  • 스케줄은 그대로 두고 LoRA 최고 학습률만 2e-4에서 2e-5로 낮춰 수렴시켰고, 논문에 보고된 성능 수준을 재현했다.
  • 여러 GPU 기준 공개 설정을 개인 GPU 한 장에 맞췄고(DeepSpeed ZeRO-2, gradient checkpointing), 공식 저장소에 없는 vLLM 서빙을 붙여 벤치마크를 돌렸다.

일하는 방식

위 작업들에서 반복되는 원칙.

  1. 01

    기술을 몰라도 쓸 수 있어야 쓰인다

    엑셀을 DB로 옮기는 도구는 PK/FK 대신 현업이 아는 말로 테이블 관계를 확인받고, 자동 수정 파이프라인의 마지막 확인은 코드 대신 배포 링크로 받는다.

  2. 02

    AI를 쓸 곳과 쓰지 않을 곳을 나눈다

    생산계획에 들어가는 메일 수치는 일부러 규칙 기반으로 뽑았다. 구매 요청 메일은 초안까지만 쓰고, 전송은 담당자가 한다.

  3. 03

    막힌 환경에서도 규칙 안의 최선을 찾는다

    외부 연결이 제한된 곳에서는 bare repository로 협업을 열었고, 웹앱이 로컬에 닿지 못할 때는 사용자 허용을 거치는 로컬 어댑터를 만들었다.

  4. 04

    내가 만든 것보다 근거를 따른다

    직접 다듬은 LightGBM이 한 번은 더 좋았지만, 평가 기간이 바뀌어도 버틴 Chronos-2를 운영 모델로 골랐다.

  5. 05

    설명되지 않는 숫자는 넘기지 않는다

    이상치는 지우기 전에 이유를 찾고(회사 밀집 지역, 유동 인구), 학습이 발산하면 설정을 바꾸기 전에 로그부터 다시 읽는다.

  6. 06

    만들고 끝내지 않는다

    엑셀을 DB로 옮겨도, AI로 그 데이터를 다룰 줄 모르면 현업의 일은 편해지지 않는다. 그래서 팀장·임원·현업 선발 인력(AI Frontier) 대상 Claude Code 교육을 보조하고, 한 사업부의 Databricks 교육을 맡고, 공장까지 다니며 자동화할 과제를 찾는다.
